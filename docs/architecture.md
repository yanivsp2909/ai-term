# AI Term: Architecture

Covers v0.1 in full and the later versions in outline. Each later version gets its full section before its first step starts.

**Core principle.** AI Term is the `ai` command (a TUI) plus a background daemon that owns every session.
- **Account logins** run the official CLIs, Claude Code and Codex, untouched, in a real PTY. AI Term never reimplements them, and never reads, copies or proxies their logins. If something works in Terminal.app, it works inside an AI Term session.
- **API keys** run AI Term's own agent from v0.4. Until then they also run on the official CLIs.

## 1. The pieces

```
 your terminal (Terminal.app, Ghostty, iTerm2… later the AI Term app)
 ┌──────────────────────────────┐
 │  ai   (client: TUI)          │  homepage, overlays, attach to a session
 └──────────────┬───────────────┘
                │ Unix socket ~/.ai-term/run/daemon.sock (framed messages)
 ┌──────────────▼───────────────┐
 │  ai daemon   (one per user)  │  sessions, PTYs, screen mirrors, keys,
 │                              │  usage, system stats, state on disk
 └──┬─────────────┬─────────────┘
    │ node-pty    │ node-pty
  claude        codex  …        each agent in its own PTY
```

> **Concept: daemon.** A program that keeps running in the background with no window of its own. The daemon owns the agents, so closing `ai` (or the whole terminal) doesn't kill them. Running `ai` again reconnects to the same daemon and shows the same agents. tmux works the same way. Code: `src/daemon/`.

> **Concept: PTY.** A pseudo-terminal: a kernel device pair that makes a program believe it's talking to a real terminal. The program gets a size (cols × rows), can switch to raw mode, and receives Ctrl+C as SIGINT. `node-pty` creates one and starts the agent attached to it. The daemon writes keystrokes in and reads raw bytes (text plus escape codes) out. Without a PTY, Claude Code and Codex refuse to run or render garbage. Code: `src/daemon/pty-host.ts`.

> **Concept: headless terminal (screen mirror).** `@xterm/headless` is xterm.js without a display. It reads the same bytes the agent prints and keeps the screen in memory as a grid of cells. The daemon keeps one per session, called the mirror. It lets the daemon redraw a session for a client that just attached, and lets the homepage show a live preview. Code: `src/daemon/mirror.ts`.

> **Concept: Unix socket.** A local "network connection" that is a file on disk (`~/.ai-term/run/daemon.sock`). Only processes that can open the file can connect, and we make the file readable only by you. No TCP port, nothing reachable from the network or from a web page. Code: `src/daemon/server.ts`, `src/client/connection.ts`.

**One package, one binary.** Running `ai` with no arguments opens the TUI. `ai daemon` is the internal entry point the client uses to start the daemon. Other subcommands: `ai doctor` (environment checks), `ai daemon stop`, `ai --version`.

**Runtime:** Node.js ≥ 22, TypeScript strict. Bun is not used, because node-pty is a Node native module (D25, verified in v0.1.1).

**node-pty version:** pinned to exactly `1.2.0-beta.15`, with its install scripts approved in `package.json` (npm 11 doesn't run a package's install scripts unless the project approves them). 1.1.0 ships its macOS `spawn-helper` without the execute bit, so every spawn fails with `posix_spawnp failed`, even with its scripts approved. Never a hand-written `chmod`. Move to the stable 1.2.x once it's released.

**TUI renderer:** our own cell renderer (D26), chosen by the v0.1.2 spike.
- **How it works:** the screen is a grid of cells (character, colors, bold), diffed against the previous frame. Only changed cells are written, wrapped in synchronized-output escapes (`\e[?2026h` … `\e[?2026l`) so the terminal paints each frame at once.
- **Why:** with a live preview, Ink used 46% CPU and 17.6 ms keystroke latency (p95). The grid used 14% and 3.1 ms (`docs/spikes/v0.1-tui-renderer.md`).

## 3. Daemon lifecycle and files

**Start.** `ai` tries to connect to the socket. If that fails, it starts `process.execPath <path to cli> daemon`:
- detached, with stdin/stdout/stderr ignored, then `unref()`; structured diagnostics use the daemon logger, never raw CLI/process streams
- the client then retries the connection for up to 3 s

The daemon takes an exclusive lock (`run/daemon.pid`, created with `O_EXCL`) so only one daemon runs. A stale pid is checked with `process.kill(pid, 0)`; a pid that belongs to another user, or to a process that started more than 2 s after the lock was written (`ps -o etime=`, pid reuse after a crash and reboot), is stale too.

**Handshake.**
1. The client sends `hello {protocol, version}`.
2. On a protocol mismatch the daemon answers `helloMismatch`.
3. The client then shows "AI Term was updated. Restart the background service? (N agents running will be stopped)". It never restarts silently.

**Stop.** `ai daemon stop` attempts every session stop and settles all results before cleanup. It sends SIGTERM, then SIGKILL after 3 s, then waits at most another 3 s for the exit callback. Failed stops log session IDs only (B15). With zero *live* sessions and zero clients for 10 minutes, the daemon exits on its own. Exited records don't keep it alive.

**Daemon restart (D32).** Finished sessions keep their real status, exitCode, statusDetail and statusSince. Only records that were starting or running become `exited` with null exitCode and detail "background service restarted". Saved PIDs are never signalled. The scrollback is lost; the record stays until you remove it.

**Write failures (D33).** A failed log/state write, including ENOSPC, never stops the daemon or agents. State writes retry on the next change. The homepage shows a persistent error-colored warning with fixed text, and clears it after the affected writer succeeds; simultaneous log/state failures clear independently. Usage settings read failures retain the last validated price overrides, warn once while failing, and clear after a successful read (B13). **Unreadable state (B24, 2026-10-14).** If `state.json` fails to read (I/O, unsafe or oversized), parse, validate (any bad session record) or migrate, the daemon never overwrites it: `moveAside` (`store.ts`) renames it to `state.json.corrupt-<ISO timestamp>` (a `-N` suffix if taken), sets 0600 on a regular file of ours, and the daemon starts with no sessions and no worktree records. The log gets `Agent list could not be loaded (<stage>)` and nothing from the error or file; each homepage gets the event `daemon.notice {text}` (`couldn't read your agent list; saved it as <file>`) after its `sessions.list`, for the daemon's lifetime, and shows it as an ordinary note (a warning would hide every other note). If the rename itself fails, the daemon stops with a fixed log line and the file untouched. Lost worktree records leave their folders as unrecorded, so S14 refuses to delete them. A terminal mirror failure instead marks only that session failed with fixed detail `terminal mirror failed`, revokes its telemetry, and attempts to stop it; removal must complete that stop before forgetting the record (B14).

**Files.** `~/.ai-term/` is mode 0700. The daemon refuses to start if it is a symlink or owned by another user.

| Path | Contents | Mode |
|---|---|---|
| `settings.json` | theme, default model/engine/folder, permission default (always `ask`), preview size, budget, key **metadata** (id, provider, label, last4, endpoint, deployments, last test result) | 0600 |
| `state.json` | session records (section 5) and worktree records `{path, branch, repo, baseBranch, baseCommit, createdAt}` (v0.3.2, §12.3); a worktree record outlives its agent | 0600 |
| `usage/YYYY-MM.jsonl` | one usage event per line (section 9) | 0600 |
| `run/` | `daemon.sock` (0600), `click.sock` (0600, notification clicks, v0.2.7), `daemon.pid` | 0700 |
| `launch/click-*/ai.command` | generated D43 Terminal launcher, removed when it runs or after 60 s; leftovers swept at daemon start | 0700 |
| `logs/daemon.log` | redacted log, rotated at 5 MB; 3 files in total (`daemon.log`, `.1`, `.2`) | 0600 |
| `worktrees/<repo-name>-<path hash>/<slug>/` | one git worktree per new AI agent on `ai/<slug>`; retained when its list record is removed (D44); deleted only through S14 | 0700 for private layout directories |
| `sessions/<id>/` | per-session generated files (hook settings from v0.2), deleted with the session | 0700 |
| `budget-reservations.json` | v0.6.1 (B25): AI Term agents' granted, unsettled request worst cases `{v:1, reservations:[{id, sessionId, provider, model, amountUsd, at}]}`; whatever is left at the next daemon start is booked at its worst case | 0600 |

Writes are atomic: write to a temp file in the same folder, `fsync`, `rename`.

**Keys are never in any of these files.** They live in the OS keychain (section 8).

## 4. Protocol (client ⇄ daemon)

Frames on the socket: `uint32 BE length` + `uint8 type` + payload. The length counts the type byte plus the payload, not itself. Max frame 4 MiB; a bigger or malformed frame closes that connection.

**Ids:**
- `id` on a control message is only the request/response correlation id.
- The session a message targets is always `sessionId`.

| Type | Payload |
|---|---|
| `0x01` control | UTF-8 JSON: `{id?, kind, ...}`. Requests carry `id`; responses echo it; events have no `id` |
| `0x02` output | 36-byte ASCII session id + raw PTY bytes (daemon → client) |
| `0x03` input | 36-byte ASCII session id + raw bytes (client → daemon, attached sessions only) |

`sessions.text` is one request returning at most 5 MiB of UTF-8 plain text. To preserve the 4 MiB frame limit, the wire sends one or more control responses with the same request `id` and `copy:{sessionId,text,truncated,more}`. Each text chunk is at most 1 MiB and ends at a complete Unicode code point. The client validates session identity, consistent truncation metadata, at most six chunks and the total byte cap, then joins them before resolving the request. Copy text never becomes a preview/output event and is neither logged nor written to disk. The client applies generic border/decoration/blank-line cleanup for `/copy all`; `/copy` and c use that same cleaned text with the v0.2 last-reply limitation note. First-message drafts preserve multiline/large pasted fragments as in-memory tokens and expand for `sessions.create`; the shared validator limits combined text to 16 KiB UTF-8. Agent spawn-error logs use fixed text because an error may include first-message argv.

**Socket trust (D35).** Any process running as the user may use the private socket, like ssh-agent. No token: a same-user agent could read a token file too. This is an accepted risk; untrusted agents stay in Ask mode.

The daemon validates every control message at runtime with hand-written validators in `src/shared/validate.ts`. Clients are treated as untrusted input even though they're local. Unknown `kind` → error response.

`SystemStats` carries numbers only: no process name, command line, user or pid ever crosses the socket. `validateSystemStats` accepts exactly these keys (finite, non-negative, percentages ≤ 100, used ≤ total, at most 1,000 sessions). The daemon checks every sample with it before sending, and the homepage checks every event with it on arrival.

`SessionInfo` gains `taskUsage?: {tokens, costUsd: number | null, unknownPrice?: true}` in v0.6.1 (cost per task; null dollars on a subscription); `settings.set` accepts `taskCost: boolean` and (v0.6.3) `handoff: boolean`; v0.6.2 adds `presets: Record<name, Preset>` and `presetsEnabled: boolean`, and `sessions.create` takes `useWorktree?: boolean` (a preset's worktree on/off for that one agent; absent means the saved setting). `Preset` (`src/shared/presets.ts`) = `{engine, model, effort, auth: AuthRef, permission, cwd, worktree, firstMessage?}`: exact keys, the create validators per field, names `^[a-z0-9][a-z0-9-]{0,31}$`, at most 20, first message ≤ 4 KiB; a key is named by id only. Presets live in settings.json under its 16 KiB cap and are checked on every settings read and write. Don't ask is allowed in a preset only because the user chose it before saving (D13 still forbids it as a saved default) and the started card shows the red `!`. `SessionInfo` in v0.1.7 = `{id, title, engine, model: string | null, auth: {kind:'account'} | {kind:'key', keyId, provider, keyLabel, last4}, authMethod?: 'subscription' | 'api-key' | 'unknown', effort?: Effort | null, conversationId?: UUID (Claude), cwd, permission, status, statusDetail, statusSince, exitCode, createdAt, lastOutputAt, ctxPercent: null}`. v0.3 (2026-10-14) adds `login?: true` on sessions started by /login, so /retry reruns the login. v0.2.2 extends ctxPercent to 0–100 or null and adds lastActivity {tool, at} or null, optional only for legacy records. Old shell records without authMethod load unchanged. Null model means CLI default and adds no model argument. Engine status responses carry only the five listed fields; auth views accept only documented metadata. Key requests, usage (v0.1.8b), and `system.subscribe` (v0.1.8a) are implemented.

`UsageSummary` has `today`, `week`, and `month` periods, each `{costUsd, tokens, cachedTokens?, unknownPrice, providers:[{provider,costUsd,tokens,cachedTokens?,unknownPrice}]}`. `cachedTokens` (v0.2.4a fix, B23) is the cache-read share already inside `tokens`; the daemon always sends it, and it is optional only so a newer client accepts an older daemon's summary. Codex field meanings, from the installed 0.160.1 binary: `response.completed` carries the Responses API usage (`input_tokens`/`input_tokens_details`, `output_tokens`/`output_tokens_details`); `input_token_count` includes `cached_token_count` (Codex itself also exports `non_cached_input_tokens`), and `output_token_count` includes `reasoning_token_count`. So tokens = input + output, and cost = uncached input × input rate + cached × cache rate + output × output rate. The newer `cache_write_token_count` is not read. Cost is the sum of known estimates; `unknownPrice` preserves the fact that some usage is unpriced. Budget settings are `{daily,weekly,monthly}` in USD, with null meaning none. `priceOverrides` maps a deployment id to `{input,output,cacheRead?}` USD per million tokens. All amounts are finite and nonnegative; settings amounts are capped at one billion. Diagnostic names are a fixed usage allowlist and values are numeric only.

`KeyView` = `{id, provider: 'anthropic' | 'foundry' | 'openai', label, last4, endpoint?, deployments?, lastTest?}`. There is **no** request that returns a secret. `keys.add` is the only message that carries one, client → daemon. The masked form clears its field before handing the request to the connection and clears the request object immediately after synchronous serialization. No secret is drawn/echoed or captured by debug input logging.

## 5. Sessions: spawn, mirror, size, exit

**Record** (in `state.json`): everything in `SessionInfo` plus `pid` and the spawn recipe *without* env or secrets (engine, model, auth ref, cwd, permission, effort, Claude conversationId).

**Create (v0.1.7).** The server validates every field, including existing-directory cwd, model id or null, account or key reference auth, permission, sanitized title, and firstMessage ≤ 16 KiB with no NUL. The manager checks the engine again before spawning, using the same own-provider env cleanup. Missing engine/login errors are allowlisted and shown inline; a rejected preflight creates no record. Each session gets a fresh recipe and env. A key reference is checked against the engine/provider; Foundry model must be in a saved ready result. The secret is read only after all metadata/CLI/argv checks, immediately around spawning, and the env reference is cleared afterward. Missing Keychain credentials refuse creation with a clear error. Login uses account auth with `login:true`, Ask, no first message: Claude `auth login`, Codex `--no-daemon -c check_for_update_on_startup=false login`; no existing CLI credential files are read. Shell sessions remain available through `ai debug shell`.

**Lifecycle** (owned by `session-manager.ts`):
```
create → starting ──first output──▶ running
running ⇄ waiting ⇄ done          (exact from v0.2 hooks; in v0.1 a live process = running)
any ──exit 0──▶ exited      any ──exit ≠ 0 / spawn failure──▶ error
```
A process exit always wins over a late status event.

**Mirror.**
- Every output chunk goes to the session's `@xterm/headless` terminal (scrollback 5,000 lines) before it goes to any client.
- Cell widths come from `@xterm/addon-unicode11` (`src/shared/unicode-width.ts`), in this mirror, the homepage preview mirror and the homepage grid alike. xterm's built-in Unicode 6 table counts most emoji as 1 cell, which misaligns every cell after one.
- On attach or preview, the daemon sends `@xterm/addon-serialize`'s snapshot first, then live output. The snapshot carries the cols × rows it was captured at.
- **Snapshot size:** a snapshot must fit one 4 MiB frame. The daemon trims old scrollback until it fits. If the visible screen alone doesn't fit (pathological styling), the request fails with a clear error. Chunked snapshots are a later protocol change, only if that ever happens in practice.

**Size rule** (the one that makes the preview work):
- **Attached:** the session's PTY and its mirror take the attached client's terminal size.
- **Not attached:** they take the **preview size**, which the homepage reports with `layout.previewSize`.
- So switching the selection on the homepage never resizes anything. Entering a session resizes once, and coming home resizes once. Claude Code and Codex redraw on SIGWINCH.

**Terminal queries.** Agents ask the terminal things (cursor position, colors, device attributes).
- **Attached:** your real terminal answers through the client's input.
- **Nobody attached:** the mirror's own `onData` replies are written to the PTY instead, so an agent never hangs waiting for an answer. Replies are budgeted per session (16 KiB burst, 4 KiB/s; `src/daemon/reply-budget.ts`) because node-pty queues writes without limit; a session that floods queries gets the rest dropped.
- **Never both at once.**

**Flow control.** Three separate rules:
- **The mirror:** has its own bounded queue. If the mirror can't keep up, it pauses the PTY until it catches up, even with no client connected.
- **An attached client** (v0.1.4): if its socket buffer exceeds 1 MB, the daemon pauses that PTY and resumes it below 256 KB.
- **Preview subscribers:** never pause a PTY. One that falls behind is dropped from live output and gets a catch-up snapshot when it drains.

**Stop.** SIGTERM to the process group, then SIGKILL after 3 s.

**Exit.** The daemon records the exit code and keeps the mirror and record until `sessions.remove`.

## 6. Attach (full-screen session) and the home key

When you enter a session, the client:
1. switches your terminal to the alternate screen and raw mode
2. sends `sessions.attach` with the real size
3. writes the snapshot
4. replays the agent's terminal modes: cursor keys, keypad, bracketed paste, mouse tracking and encoding, focus events, cursor visibility. Some of these aren't in xterm's public `modes` (mouse encoding, cursor visibility), so the mirror tracks them from the output stream itself. Order matters: reset every mouse mode first, then enable the one in use.
5. pipes output frames straight to stdout and stdin straight to the session

**Ownership.**
- One client is attached to a session at a time. A new attach takes over, and the previous client gets `session.detached {sessionId, reason: "attached elsewhere"}`.
- A stale detach from the old client can't detach the new one.
- Input frames are accepted only from the current owner; everything else is dropped and logged without content.

AI Term draws nothing over the session in v0.1 (the frame bar comes in v0.2).

**Home key: Ctrl+E** (D11). One key, no modes.
- **Inside any session** (Claude Code, Codex, later AI Term's agent): Ctrl+E goes to the homepage, and the agent keeps running. The client never forwards it, in any of the forms it can arrive in:
  - the raw byte `0x05`
  - the kitty keyboard protocol (`CSI 101;5u`, including event-type variants)
  - xterm modifyOtherKeys (`CSI 27;5;101~`)
  
  Sequences split across reads are handled. Inside a bracketed paste (`\e[200~` … `\e[201~`), a `0x05` is pasted text, not the home key.
- **On the homepage:** ⏎ goes back into the selected agent; `/exit` quits `ai`. The agents keep running in the daemon.
- **Ctrl+Shift+E:** most terminals send the same byte, so it works too.
- **⌘E:** can't be used. Terminal.app and iTerm2 keep ⌘ keys for themselves and never pass them to a program.
- **Cost:** inside sessions, Ctrl+E no longer jumps to the end of the line. Use End (Fn+→) instead.

On the home key the client sends `sessions.detach`. It then resets every mode the agent may have turned on (mouse, bracketed paste, focus events, cursor keys, kitty keyboard, cursor visibility, colors), leaves the alt screen and raw mode, and redraws the homepage. The agent keeps running.

**Cleanup is guaranteed** on every way out: home key, session exit, takeover, daemon death, uncaught client error, SIGTERM, SIGHUP and SIGQUIT. Reset includes mouse/paste/focus modes, alternate-scroll `?1007`, window title (empty default), palette (OSC 104), default foreground/background/cursor colors (OSC 110/111/112), and cursor shape (DECSCUSR 0), then leaves alt screen and raw mode and sends detach. SIGKILL cannot run cleanup.

**Client signals (D34).** SIGTERM/SIGHUP quit the client with exit 143/129 after cleanup; SIGQUIT exits 131. The client sends no stop request and never signals a session process. Daemon and sessions keep running.

**`/exit` chain.** The chain is: session → home → shell.
- Typing `/exit` inside Claude Code or Codex is *their* command: the agent exits, the session becomes `exited`, and the client returns home.
- `/exit` typed on the homepage quits `ai`. The daemon and the other agents keep running.
- Running `ai` again brings it all back.

**Resize while attached:** SIGWINCH in the client → `sessions.resize`.

**Mouse and selection inside a session:** passed through untouched. The agent's own selection and copy work exactly as in Terminal.app.

### 7.2 Arguments (`buildArgs`, pure, unit-tested)
- Executable: `resolveExecutable('claude' | 'codex', PATH)` walks PATH and returns the absolute path of the first regular, executable file. Not found → the session goes to `error` with "claude not found in PATH".
- Model: null ("CLI default") adds nothing; otherwise one argv element `--model=<id>`, only if `isValidModelId(id)`: `/^[A-Za-z0-9][A-Za-z0-9._:\[\]\/-]{0,79}$/`. The leading-character rule plus the single-element form mean a "model" can never be read as another flag.
- First message: the last argv elements are `--` and then the message as one element. Both CLIs take a positional prompt and accept `--`. v0.1.6 keeps argv delivery: Codex displayed the exact prompt in live runs; Claude paused at folder trust before prompt execution. No paste fallback or automatic trust acceptance was added.
- Effort: absent/null (`CLI default`) adds nothing. Claude's installed help documents `low`, `medium`, `high`, `xhigh`, `max`: one argv element `--effort=<level>`. Codex rust-v0.160.1's config and ReasoningEffort wire enum document `none`, `minimal`, `low`, `medium`, `high`, `xhigh`, `max`, `ultra`, `persistent`: `-c` followed by one argv element `model_reasoning_effort="<level>"`. Shared validation enforces engine-specific values before argv. Individual models may accept fewer CLI-supported levels. `/settings` may save `defaultEffort`; incompatible effort resets to CLI default when switching engines.
- Conversation identity/resume: new Claude agents get an AI Term-made UUID in `--session-id=<uuid>` and the public record. A `sessions.resume` request identifies the selected exited/error AI Term record; the daemon uses that record's recipe, never client-supplied overrides. Claude uses `--resume=<conversationId>` without the new-session flag; older records without an id refuse with a note. Codex help documents `resume [SESSION_ID] [PROMPT]`, but AI Term cannot learn a new Codex id through documented spawn flags, so it launches `codex resume` with the original folder/options and lets the user choose. No CLI session files are read. Concurrent resumes reserve the conversation until the new record exists, preventing duplicate Claude spawns; shells/live records cannot resume.
- Codex daemon: every Codex session's argv starts with `--no-daemon`, exactly once (D41). Without it the Codex TUI may join a shared background server started elsewhere, and that server's env and config win over this session's env and `-c` overrides. Codex rejects the flag when it appears twice.
- Codex update check: right after `--no-daemon`, every Codex session passes `-c check_for_update_on_startup=false`, Codex's own setting (`codex-rs/config/src/config_toml.rs` at `rust-v0.160.1`). Otherwise a fresh session can open on the "Update available" menu, where Enter means "Update now".
- Foundry on Codex: `-c` overrides only, nothing written to `~/.codex` (from docs; the live test is pending in `docs/spikes/v0.1-cli-facts.md` #3 and #4). Each override is one argv element:
  - `--no-daemon` (the same single flag every Codex session starts with; also required for invocation-local config overrides)
  - `-c model_provider="aiterm_foundry"`
  - `-c model_providers.aiterm_foundry.name="AI Term Foundry"`
  - `-c model_providers.aiterm_foundry.base_url="<endpoint>"`, for example `https://narvis-resource.openai.azure.com/openai/v1` (no `api-version` on `/openai/v1`)
  - `-c model_providers.aiterm_foundry.env_key="AITERM_FOUNDRY_KEY"`
  - `-c model_providers.aiterm_foundry.env_http_headers={"api-key"="AITERM_FOUNDRY_KEY"}` (the value is the env var's *name*, never the key)
  - `-c model_providers.aiterm_foundry.wire_api="responses"`
  - `-c model_providers.aiterm_foundry.requires_openai_auth=false`
  - `--model=<deployment>`

  The endpoint goes into a `-c` value, so it's validated first: `https://`, a hostname, no quotes or whitespace.
- **Permission mode:**
  - `ask` (default) adds explicit ask flags (D40), so a bypass in your own CLI config can't turn Ask into Don't ask: Claude Code `--permission-mode=default`; Codex `--ask-for-approval=on-request` plus `--sandbox=workspace-write`. Claude Code 2.1.296's help lists this mode as `manual`; the CLI maps `manual` to its canonical `default`, which it accepts.
  - `auto` is Claude-only and adds `--permission-mode=auto`, documented in installed help. Codex has no distinct documented auto option; validation rejects it. Auto is per session and cannot be saved as a default.
  - `dontAsk` is chosen per session only, never as a saved default, and is shown with a red `!`. It adds exactly one flag per engine: Claude Code `--permission-mode=bypassPermissions`; Codex `--ask-for-approval=never` plus `--sandbox=workspace-write`. Codex stays sandboxed: don't-ask never means `--dangerously-bypass-approvals-and-sandbox`.
  - Flag spellings verified in v0.1.1. Claude Code also has a mode literally named `dontAsk`, which denies tools that aren't pre-approved. That is not our Don't ask; we never use it.
- Never passed: `--dangerously-skip-permissions`, `--yolo`, `--dangerously-bypass-approvals-and-sandbox`, `--full-auto`, `danger-full-access`, `--approve-for-me`.

## 8. Keys (OS keychain)

> **Concept: OS keychain.** The operating system's encrypted password store: Keychain on macOS, Credential Manager on Windows, Secret Service (GNOME Keyring / KWallet) on Linux. The OS encrypts it with your login and only gives entries back to your user account. We use `@napi-rs/keyring` to reach all three from Node. Code: `src/daemon/keys.ts`.

- Each key is an entry with service `ai-term` and account `<provider>:<keyId>`. Its metadata (label, last4, endpoint, deployments) lives in `settings.json`. last4 is computed once, when the key is added.
- `keys.add`: validate the input (provider known; the secret is a non-empty string ≤ 512 chars with no whitespace; the endpoint is `https://`), write to the keychain, then store the metadata. If the keychain is unavailable, refuse with a clear message. There is never a plain-file fallback.
- **Import from .env.**
  1. `keys.scanEnvFile` reads the file in the daemon and returns only the *names* of known key variables (`ANTHROPIC_API_KEY`, `OPENAI_API_KEY`, `AZURE_OPENAI_API_KEY`, …).
  2. You pick which ones to import.
  3. `keys.importEnv` moves the values straight into the keychain.
  
  The file is never modified, and the UI suggests deleting it.
- **Foundry test.** For each deployment, one `POST <endpoint>/responses` with `{model: <deployment>, input: "ping", max_output_tokens: 16}` and a 15 s timeout. On 404 or 400 it tries `chat/completions`. The result per deployment is ready / not a chat model / error (HTTP status + the provider's error code, never the key). Requests go only to the configured `https://` endpoint, with the key in the `api-key` header.
- **Foundry binding (B12, v0.2.7).** settings.json is writable by any process running as the user, so it can't decide where a secret goes. A Foundry key's Keychain entry holds `{"v":1,"secret","endpoint","deployments"}`; settings.json keeps a display copy. `withSecret` refuses the key if the copy's endpoint or deployments differ (`Foundry key details changed outside AI Term; add the key again`) or if the entry is unbound: a bare secret saved before v0.2.7, or malformed (`Foundry key must be added again to bind its endpoint`). It never trusts on first use. Callers get the bound values: `keys.test` probes only the bound endpoint and deployments, and a Foundry spawn refuses argv whose `base_url` or deployment isn't bound. `lastTest` stays in settings.json; it only picks among bound deployments. Residual: the Keychain item's ACL trusts the node binary, so a same-user node process could still read it; that's the D35 boundary.
- **v0.6.5 providers** (§12.12): xAI, Moonshot, Z.ai, OpenRouter and Vertex keys go to fixed hosts in code; a Bedrock key's region is bound in its Keychain entry like a Foundry endpoint; Ollama has no key and no Keychain entry (metadata only, `http://127.0.0.1:<port>`).
- Removing a key deletes the keychain entry and its metadata. Sessions already running keep their env until they exit.
- `keys.ts` is the only Keychain boundary, using AsyncEntry and service `ai-term`, account `<provider>:<UUID>`. Tests inject a vault or a unique `ai-term-test-*` service, never the production service. Native failure is a fixed clear error, with no file fallback; a failed metadata add rolls the new Keychain entry back.
- Metadata writes serialize with settings patches by file path so a theme/default change cannot erase keys. Metadata is validated on load/response; no private fields accepted. Keys shorter than 16 characters have an empty displayed suffix, so last4 never reveals most of a short credential. A quoted .env value may carry a trailing comment. A failed import rolls back each created entry separately and names any entry it could not remove.
- Env parsing accepts simple optional `export`, quoted/unquoted assignments from an owned, non-symlink regular file ≤1 MiB. Only recognized selected credential names are imported; no evaluation, expansion or source file writes. Foundry import additionally requires `AZURE_OPENAI_ENDPOINT` and `AZURE_OPENAI_DEPLOYMENT` in that file; scan still returns credential names/providers only. Failed multi-key import rolls back entries it created. UI suggests deleting the source file.
- Foundry transport uses HTTPS POST and does not follow redirects; 15 s whole-request deadline, 64 KiB reply cap. Only HTTP status and a validated provider code are returned, never body/error messages. Chat fallback success means “not a chat model” for Codex (not ready). Client request timeout covers the bounded number of sequential probes.
- L10: `AI_TERM_DEBUG` logs input counts, never bytes or hex. L12: auto-started daemon stdout/stderr are ignored; uncaughtException/unhandledRejection run redacted logger plus clean shutdown. Startup diagnostics go through the CLI redactor.

## 9. Usage, cost, budget

- **Scope:** every session whose effective auth is an API key. That's AI Term's keyed sessions, plus Claude Code or Codex when their own login is an API key (D31). Subscription sessions show `sub` and are not counted in the totals (from v0.6.1 they report tokens for their own task total only, below). AI Term never reads Claude Code's or Codex's own files to count anything.
- **Source per engine:** OpenTelemetry the CLI exports itself, received by a local OTLP/HTTP receiver in the daemon. Payloads are JSON (`http/json`), never protobuf. Each eligible session gets 32 random bytes encoded as hex, held in memory and revoked at exit or failed spawn. Claude receives the header through env; Codex uses an invocation-local exporter `-c` override (D52). Credentials and spawn env/argv are never logged or persisted.
  - **Claude Code (metrics only):**
    - env: `CLAUDE_CODE_ENABLE_TELEMETRY=1`, `OTEL_METRICS_EXPORTER=otlp`, `OTEL_LOGS_EXPORTER=none`, `OTEL_EXPORTER_OTLP_PROTOCOL=http/json`, `OTEL_EXPORTER_OTLP_METRICS_ENDPOINT=http://127.0.0.1:<port>/v1/metrics`, `OTEL_EXPORTER_OTLP_METRICS_HEADERS=x-ai-term-session=<credential>`, `OTEL_METRICS_INCLUDE_SESSION_ID=true`, `OTEL_METRIC_EXPORT_INTERVAL=10000`
    - metrics read: `claude_code.token.usage` (input / output / cacheRead / cacheCreation) and `claude_code.cost.usage` (USD, Claude Code's own estimate)
    - points are delta (live test #5). Cumulative points count the increase per session/model/type/start timestamp, or the full value after a counter drop/new series; interleaved deltas advance that baseline. Repeated exports dedupe by session/model/type/start/time. Numeric strings are accepted, invalid values are discarded, missing timestamps remain diagnostic-only. Cache creation and cache reads are input tokens, with cache reads also recorded separately.
  - **Codex (logs):**
    - `-c otel.log_user_prompt=false`, `-c otel.exporter={otlp-http={endpoint="http://127.0.0.1:<port>/v1/logs",protocol="json",headers={"x-ai-term-session"="<credential>"}}}`
    - only `input_token_count`, `output_token_count`, `cached_token_count`, `reasoning_token_count` from `codex.sse_event` / `response.completed` are read, plus model if present (otherwise selected model). rust-v0.160.1 emits input/output as strings, so numeric strings are accepted. Reasoning is already part of output and is diagnostic-only; it is never added twice. The rest of every event is dropped unread, because tool output in other events can contain your code.
    - cost is estimated from the price table
  - Claude's live test #5 is confirmed; Codex live test #6 remains for Yaniv. Implementation matches the public rust-v0.160.1 source (`otel/src/events/session_telemetry.rs`, `sse_event_completed` and `otel/src/provider.rs`, HTTP exporter headers). `ai debug usage` shows the receiver port and last ten minutes of candidate allowlisted attribute names/numeric values; it shows neither string values nor bodies nor credentials. Diagnostics are bounded to 1,000 candidate entries and held in memory only.
- **Receiver:** starts with the daemon on a random `127.0.0.1` port and follows S12: exact Host, no Origin, JSON only, POST metrics/logs only, 1 MiB limit, credential length check and `timingSafeEqual`, 200 `{}` on success. An oversized body up to 4 MiB is read and discarded (never kept past 1 MiB) before the 413, because closing with unread bytes resets the connection and loses the 413, and OTLP exporters retry a reset but not a 413 (B10); larger bodies are cut. One export point above 1e9 tokens or 10,000 USD is dropped as forged, totals saturate at 2^53−1, dedupe keys are bounded, and an unsafe month file is skipped with a warning that lasts until restart. Each live session may append at most 120 unique records in a 60-second window (1,800 for AI Term's agent, which reports every request as it happens, v0.4.2) starting at its first accepted record; excess records are dropped with one fixed log line per window, and revocation clears the cap state (B19). Malformed/oversize/auth failures have fixed responses; unexpected errors log fixed text. Header/body contents never reach logs. Same-user socket access remains the accepted D35 trust boundary.
- **Event** (`usage/YYYY-MM.jsonl`): `{ts, sessionId, provider, model, inputTokens, outputTokens, cachedTokens?, costUsd, costSource: 'cli-estimate' | 'price-table' | 'worst-case'}` (`worst-case`, v0.6.1: a held request whose usage never arrived, zero tokens). Neither is a bill: both are estimates and the UI says so.
- **Price** when the CLI doesn't report cost: `data/usage-prices.json`, fetched 2026-10-12, contains only Anthropic/OpenAI/Azure input/output/cache-read prices per million tokens. `scripts/update-prices.ts` trims an explicitly downloaded catalog offline. Foundry looks up the deployment id in overrides, Azure, then OpenAI. An explicit two-rate override charges its input rate to all input tokens without inventing a cache discount; a catalog missing a cache rate charges cached input at the input rate (v0.4.2: an upper bound, so budgets never lose cache hits). Unknown model prices remain null and the UI shows `price ?`. Historical estimates are not repriced. Own-login Codex API-key sessions are attributed to OpenAI because engine status does not reveal the configured provider; keyed Foundry sessions use Foundry/Azure.
- **Summary:** today / this week (Monday start, local time) / this month, as cost and tokens, by provider. Incremental per-day buckets rebuild from private monthly JSONL files at startup; local midnight emits the newly selected periods. Dedupe lasts for each live session and is runtime-only; old credentials are revoked at restart, so stale sessions cannot replay into a new daemon.
- **Write failure:** usage directories stay 0700 and files 0600. A failed append rolls back any partial line, warns on the homepage and retries unsaved records on the next export; agents and the daemon keep running (D33). Pending unsaved records are memory-only and can be lost if the daemon dies before recovery. Unsafe/unreadable history logs fixed text; an inaccessible history path also warns.
- **Budget:** optional daily / weekly / monthly limit in settings.
  - Empty-field `b` opens three USD fields; Enter saves, Esc cancels. `/settings` price row or `p` opens deployment/input/output prices per million. The Usage panel uses a single `≈` estimate marker, bold spend and compact tokens; subscriptions and unknown-auth sessions receive no AI Term telemetry settings. Login/debug-shell sessions are excluded. Existing sessions must be restarted to pick up telemetry.
  - **v0.1:** crossing a limit turns the top-bar count amber and shows a warning line. Nothing is blocked.
  - **v0.4:** AI Term's own agent stops *before* a request that would cross the limit.
  - **Claude Code and Codex:** AI Term can only stop the session after the fact, never block a request in flight.
  - **v0.6.1 (B25), budgets across agents:** the daemon holds the budget (`src/daemon/budget-ledger.ts`). Before each model request AI Term's agent sends `{kind:'budget.reserve', model, amountUsd}` on its engine-bound `/v1/agent/ai-term` route, `amountUsd` being the request's worst case from `RunLimits.check` (input estimate plus the full output allowance at known prices). The ledger grants `{grant:{id}}` only if every daily/weekly/monthly budget still fits counting every live reservation; check and insert are one synchronous step, so of two agents racing for the last of a budget exactly one gets the grant. Otherwise `{refused:{budget, spent, reserved, limit}}`; the agent checks again with fresh facts (which carry `reserved`, the total held) up to three times, then pauses with the budget ask. No answer (204) means nothing is sent: a restarted or unreachable daemon fails closed. After the request the agent sends `{kind:'budget.settle', id, worstCase}` in its reporter queue right behind the request's usage post: `false` releases it (its usage is counted already), `true` books the worst case as a `worst-case` usage record (cut off, failed after the provider answered, no counts, usage not taken). The daemon also books a session's reservations when it exits, any reservation after 20 minutes, and at start whatever `budget-reservations.json` still lists. Only the session that holds a reservation settles it; amounts are 0–10,000 USD; at most 1,000 live, 16 per session and 600 a minute per session; a reserve arriving after its agent exited is refused; an unreadable reservation file is moved aside (`.corrupt-<time>`), never overwritten. With the ledger, budget rooms subtract `facts.reserved` instead of the run's own unreported/reserved amounts (the run's spend cap still uses them). Reservation-file write failures are logged and retried (D33).
  - **v0.6.1 cost per task (D55, on by default, `/settings` o, setting `taskCost`):** every counted usage record also adds to its session's `SessionInfo.taskUsage {tokens, costUsd, unknownPrice?}` (persisted with the record). Subscription and unknown-auth Claude Code / Codex sessions now get the same telemetry settings in a tokens-only context (`UsageContext.taskOnly`): their records add tokens to their own total only and never reach Usage, a budget or a price (D27 holds for the totals). Off: no telemetry for those sessions started afterwards (running ones keep reporting until they exit), and cards and `/usage` hide the totals. Totals reach the card and state.json at most once a second. A grant spans its request's tools (the step's usage arrives after them), so the 20-minute expiry waits while the agent asks you something or runs a tool. Residual: a `budget.settle` lost after the daemon took the usage, or an exit between them, books the worst case on top of the real usage (over, never under); one grant covers the SDK's up to two retries of that request.

## 10. This Mac (system stats)

`src/daemon/sysstats.ts`, macOS only until v0.8. It samples every 1 s, and only while at least one connected client is subscribed (`system.subscribe {on: true}`). Sampling stops when the last subscriber unsubscribes or disconnects, and no process is spawned while nobody is subscribed. Each sample runs three commands in parallel with `execFile`: absolute path, argv array, 2 s timeout, 1 MiB output cap.
- **Per session:** `/bin/ps -axo pid=,ppid=,rss=,%cpu=`.
  - The daemon builds the process tree. For each live session it sums the PTY child (`node-pty`'s pid) and all its descendants.
  - ps reports %cpu per core, so the sum is divided by the core count to give a share of the whole machine (clamped to 0–100). RSS comes in KiB and is converted to bytes.
  - Only lines of exactly four numbers are read. Anything else, including a line carrying a command, is dropped whole.
- **Machine CPU:** deltas of `os.cpus()` times (busy ÷ total over all cores). The client keeps the last 10 samples for the sparkline. v0.1.7f: thirty aligned busy-machine samples averaged 43.85% here versus top 44.16% (mean difference −0.31 percentage points); no calculation change justified.
- **Machine RAM:** Activity Monitor's "Memory Used" = App Memory + Wired + Compressed. `/usr/bin/vm_stat` exposes App Memory as (`Anonymous pages` − `Pages purgeable`) × page size, Wired as `Pages wired down` × page size, and Compressed as `Pages occupied by compressor` × page size. Anonymous pages match the kernel's pageable internal count; active pages alone omit inactive anonymous memory. The sum is capped at `os.totalmem()`. v0.1.7f measured purgeable at 0.113 GiB, far below the reported ~1 GiB Activity Monitor headline gap; retain this sum until paired headline evidence identifies the difference. `ai debug stats` prints both candidate totals to support that comparison. Missing/malformed counters or purgeable exceeding anonymous invalidate the sample. Linux will use `/proc/meminfo`.
- **Network:** deltas of `/usr/sbin/netstat -ibn` byte counters on non-loopback interfaces. Each direction uses decimal B/s, KB/s or MB/s with one decimal, so light traffic remains visible. Machine-wide only, because per-process network isn't reliable on macOS.
  - Only the `<Link#N>` rows are read. They carry each interface's totals once; address rows repeat them. Rows without a hardware address have 10 fields instead of 11, so the byte columns are read from the end.
  - Only interfaces present in both samples count. A counter that went backwards voids that sample, so a rate is never negative.
  - VPN traffic is counted on both `utun*` and the physical interface.
- **First sample and failures:**
  - The first sample after a start is only the baseline for the deltas, so the first event arrives about 1 s after subscribing.
  - A failed, unreadable or reset sample is skipped. A sample still running when the next tick comes skips that tick rather than stacking.
  - A failure streak is logged once with fixed words (`System stats sample skipped (timed out)`), never the command's stderr. Recovery is logged once too.
- **Cost (v0.1.8f, 1 s interval, own built daemon, 3 live sessions):** 0.45% of one core (0.27 CPU s / 60.007 wall s). After unsubscribe, 0 stats events and 0 kqueue fork notifications over 30.004 s. Raw numbers: `docs/testing/v0.1.8f-measurements.json`.
- **Earlier cost (v0.1.8a gate, 2 s interval, own daemon, 3 live sessions):** 0.13–0.32% of one core while subscribed, averaged over 60 s across three runs. With no subscriber, kqueue `NOTE_FORK` counted 0 spawns over 30 s (87 per 60 s while subscribed: 29 samples × 3 commands).

**Calibration command.** `ai debug stats` runs independently of the daemon, takes ten diagnostic pairs started one second apart, and prints JSON with numeric values only. It includes anonymous/purgeable/App/wired/compressed/file-backed/free bytes and both RAM sums. CPU compares `os.cpus()` deltas captured at the two CPU lines from `/usr/bin/top -l 2 -n 0 -s 1`, keeping only parsed user/system/idle/busy numbers. Top startup costs mean the first result arrives later than one second; bounded pairs are staggered for subsequent one-second output. No PID/process/name/user fields or raw command output are printed. Read/parse errors produce a fixed diagnostic error. Normal homepage sampling remains one second (D46), with no top process added.

### 12.2 v0.3.1 worktree starts
- `src/daemon/git.ts` is the sole git process boundary. It uses `/usr/bin/git` through `execFile` with argv arrays, a 10-second timeout, 1 MiB output cap and `GIT_TERMINAL_PROMPT=0`. Its minimal env excludes inherited git routing and credentials, ignores global/system config, and disables hooks, fsmonitor and recursive submodules. Protocol reasons are fixed; raw git stderr never reaches clients or logs. Positional paths and refs follow `--`. Git's `-bai/<slug>` is an option value before `--`; revision discovery uses implicit HEAD (`show --no-patch --format=%H --`) because `rev-parse --verify -- HEAD` does not work. Top-level discovery has no positional ref/path.
- `src/shared/validate.ts` generates a lowercase ASCII slug using only letters, digits and `-`, with a non-hyphen first character and 40-character maximum. The alphabet is stricter than `check-ref-format`. Existing `ai/` branches and allocated paths reserve their slug; suffixes `-2`, `-3` etc. stay within 40 characters. A queue shared by starts from different socket clients reserves each allocation; an external collision retries up to five times.
- D44's concrete layout is `<AI_TERM_HOME>/worktrees/<repo-name>-<first 10 SHA-256 hex chars of canonical top-level path>/<slug>`. The default is `~/.ai-term`; tests use temporary homes. The private layout directories are real, owned, 0700 directories, checked with lstat and canonical containment. Selected subfolders are validated component by component without following a repository-controlled symlink. Missing empty/untracked subfolders are created 0700, preserving the relative `/cd` folder. No checkout, reset, stash, clean, branch deletion or worktree deletion occurs.
- Protocol first: settings `worktrees: on|off` defaults on when absent. Sessions optionally carry `worktree`, `branch` and a fixed `worktreeNote`; old records remain readable. The manager prepares a tree before the PTY spawn and persists its actual cwd; state reload and `/resume` retain metadata. Plain shells and login sessions are excluded. A non-repo, unborn HEAD, git check error or creation error starts in the original folder with a card note. Fallback notes are logged through the daemon logger.

### 12.3 v0.3.2 worktree removal (S14)
- **Record.** `state.json` holds `worktrees: WorktreeRecord[]` beside sessions, keyed by path. A start records `repo` (canonical top level), `baseBranch` (the checkout's branch when it is a plain name, read before anything is created) and `baseCommit` (the HEAD the worktree was made from). Removing an agent keeps its record; only a successful delete, or a delete whose worktree step succeeded, drops it. At load, a v0.3.1 session's `worktree`/`branch` becomes a record without repo or base. Invalid stored records are skipped with a fixed log line, which leaves their folder undeletable; since the v0.3 gate the daemon first keeps a 0600 copy of the whole file (`state.json.corrupt-<timestamp>`, `keepCopy`) and shows the same note as B24, so the next save can't erase them. Starts (v0.3 gate): only git's own "not a git repository" answer means no repo; any other git failure (timeout, unsafe path, bare repo, ownership) is `worktree off: git check failed`, logged as an error. Unreadable settings keep worktrees on. A start that fails after git made the branch, or after the worktree was added, is rolled back with the plain remove and `branch -d` (both refuse anything with work) and the empty folder's rmdir; whatever couldn't be undone is logged. Status runs with `--ignore-submodules=all` (a populated submodule has its own config, which an agent can write, and status would run its filters), and every gitlink folder that holds anything, or isn't a folder, counts as changed and enters the fingerprint; `log.showSignature=false` keeps `git show` from running `gpg.program`. Removal decides "folder already deleted" from the folder alone, not git's prunable flag (which a missing `.git` file also sets), so such a folder fails the identity check and is refused.
- **Loss check** (`inspectWorktree`, `src/daemon/git.ts`, read-only, `GIT_OPTIONAL_LOCKS=0`):
  - `worktree list --porcelain -z --` gives presence, `locked`, `prunable` (folder gone), the branch per worktree and the main checkout (first entry).
  - `rev-parse --path-format=absolute --show-toplevel --git-common-dir --absolute-git-dir` (no positional ref or path) runs in the worktree and in the repo. The worktree's top level must be its own path, both common dirs must match, and the worktree's admin dir must record `<path>/.git` in its `gitdir` file, so a rewritten `.git` file (another repo, or a sibling worktree's admin dir) can't redirect the check.
  - `status --porcelain=v1 -z --untracked-files=all --ignored=matching --` (16 MiB cap) counts changed (any tracked change, staged or not; a rename counts once), untracked (each file; a nested repository stays one folder entry and is counted as `repos` too) and ignored entries (an ignored folder counts once).
  - `ls-files -v -z --`: entries flagged assume-unchanged (lowercase tag) or skip-worktree (`S`) count as changed, because status, and git's own plain `worktree remove`, can't see edits behind those flags (review finding, RED d452a96).
  - `check-ignore -v -z --stdin` (names on stdin, each prefixed `./` because check-ignore refuses literal pathspecs) names the rule source of each ignored entry. An entry stays ignored only if that source is a `.gitignore` tracked in the repo (`ls-files -z -- <sources>`). Files hidden by `info/exclude`, a repo `core.excludesFile` or an uncommitted `.gitignore`, which the agent can write, count as untracked.
  - All other git calls run with `GIT_LITERAL_PATHSPECS=1`.
  - `for-each-ref --format=%(ahead-behind:<base>) -- refs/heads/ai/<slug>` counts commits on the branch the base lacks (git ≥ 2.41; 2.50.1 here). The base is `refs/heads/<baseBranch>` when it still exists, else the start commit (`baseSource: 'start commit'`), else, for v0.3.1 records, the checkout's current branch or HEAD (`baseSource: 'checkout'`). Only plain branch names (`[A-Za-z0-9._/-]`, no leading `-`, no `..`) reach the format atom.
  - The fingerprint is a SHA-256 of the branch tip, raw status, commit count, base ref, lock and missing flags.
- **Rules** (`src/daemon/worktree-removal.ts`): the refusals listed in S14, checked in that order. Legacy records find their repo through the worktree's common dir, and it must hash to the worktree's parent folder (D44 layout) or the delete is refused as `Original repo unknown`. Unrecorded folders under `worktrees/` are listed (at most 500) and never deleted.
- **Delete.** It runs inside the per-home queue shared with starts (`serialize` in `worktrees.ts`), plus a per-path busy set shared with `/resume`. It rechecks everything, then requires the fingerprint the client was shown, and for loss the exact branch name. Plain `remove` and `-d` let git refuse a tree or branch that changed after the check. `git worktree prune` is not run: `git worktree remove` already cleans up a folder deleted by hand, and prune would also drop git's records of other missing worktrees in that repo (for example on an unmounted drive). Nothing else in the repo is touched.
- **Known limits.** Removal runs with a 300-second timeout; the checks keep 10 seconds and a 16 MiB output cap, so a tree too large to list is refused as `Git check failed`. Agent-enabled sparse checkouts count every skip-worktree entry as changed and always need the typed confirmation. For v0.3.1 records the repo is derived from the worktree itself and pinned only by the 10-hex folder hash; forging a matching repo needs a same-user process, which could delete the folder directly anyway. A same-user process could swap a folder for a symlink in the milliseconds between the recheck and git's own remove. The private 0700 root and git's own checks narrow that window, but it is the accepted same-user boundary (D35). `branch -d` compares with the original checkout's current branch: if that isn't the recorded base, a clean delete can stop at `Worktree removed; branch delete failed`, and the branch stays for you. A start that fails after `git worktree add` (subfolder checks) still leaves an unrecorded worktree, as in v0.3.1.

### 12.11 v0.6.4 several accounts per engine: what shipped (2026-10-15)
- **Profiles.** Settings keep `accounts: [{name, engine}]` (≤ 10; names `a-z0-9-` ≤ 32; `own` is reserved for your normal login) and `defaultAccounts: {claude-code?, codex?}`. Nothing else about an account is stored by AI Term. Each profile is `~/.ai-term/profiles/<name>/` (0700; `privateDirectory` refuses a symlink or foreign owner at both levels).
- **Env (env.ts only).** An account session gets `CLAUDE_CONFIG_DIR=<profile>` (Claude Code) or `CODEX_HOME=<profile>` (Codex) through `buildSpawnEnv(..., {profileDir})`; with `own` the inherited value stays, as before. The engine check (`checkEngine(..., profileDir)`) reads that profile's login status through the CLI's own status command.
- **Login.** `/account add claude|codex <name>` saves the name, then starts the CLI's own login session (`claude auth login` / `codex … login`) with that profile folder. AI Term never reads, copies or stores the token (S11 unchanged).
- **Shared extensions.** The profile gets symlinks to `~/.claude/skills|agents|commands` or `~/.codex/prompts|skills|agents` when those folders exist (only their existence is checked); never to credentials, settings, history or projects. Nothing is written into `~/.claude` or `~/.codex`.
- **Choosing.** `AuthRef` account may carry `profile` (a name or `own`); absent means the engine's default account, else your normal login. `/account use <name|own>` or the start box `a` picks one for the next agent; `/retry` and `/resume` keep the account the agent ran on; a profile that's gone refuses with `Account not found for this engine`.
- **Limits.** One second after output settles, the visible screen (≤ 60 rows, never scrollback) is matched against whole phrases: Claude Code `… limit reached … resets 3pm`, `Claude usage limit reached … reset at 7:30 pm`; Codex `You've hit your usage limit … try again at 3:45 PM` (`limit-detect.ts`). `SessionInfo.limit {resets: 'HH:MM' | null}` is set and cleared with what the screen shows; the card reads `⏸ limit · resets HH:MM`, the homepage says it once with the choice: wait, or `/handoff <agent> claude:<account>` (the v0.6.3 handoff, same worktree, `sessions.handoff{,Plan}.account`). Display only: nothing switches accounts by itself, and an agent printing the phrase can only change what the card says.
- **Review fixes (2026-10-15).** A limit counts only from a CLI banner line (the phrase opens the line after box-drawing or glyphs), never from code or prose quoting one; a question that needs you stays above it on the card; no check after exit. Whole settings must point each default at an account of that engine. Unreadable settings refuse an account agent without an explicit account once any profile folder exists (the default can't be known); with no profiles the old fail-open start stays. A handoff resolves its account once (named, else the engine default) for both the login check and the start. With no priced key, a limited agent is refused at once (it can't write its own note). The start box keeps a picked account across a same-engine model pick and drops it for another engine or a key; `/account use` resets the model when the engine changes; `/account add` takes the name back when its login can't start; `/account rm` clears it from the next agent.
- **Accepted:** the shared-extension symlinks mean whatever the CLI writes into those folders under a profile (Codex installs bundled skills into `$CODEX_HOME/skills`) lands in your real `~/.codex/skills` or `~/.claude/...` folders, exactly as it does for your normal login; AI Term itself writes nothing there (D17's design). An entry already present in a profile folder is left as it is.

### 12.12 v0.6.5 more providers (2026-10-15)
- **Providers** (`src/shared/providers.ts`): xAI `https://api.x.ai/v1`, Moonshot `https://api.moonshot.ai/v1`, Z.ai `https://api.z.ai/api/paas/v4`, OpenRouter `https://openrouter.ai/api/v1` (OpenAI-compatible Chat Completions, key as the bearer token, `@ai-sdk/openai-compatible` with `includeUsage`); Google Vertex express mode `https://aiplatform.googleapis.com/v1/publishers/google` (`x-goog-api-key`, `@ai-sdk/google-vertex/edge`, so google-auth-library is never loaded); Amazon Bedrock `https://bedrock-runtime.<region>.amazonaws.com` (bearer API key, `@ai-sdk/amazon-bedrock` with explicit key, region and base URL, so no `AWS_*` variable is read); Ollama `http://127.0.0.1:<port>/v1` with no key and no Authorization header. Hosts are constants in code, never from settings.json; Bedrock's region is bound in the Keychain entry exactly like a Foundry endpoint (B12, `Bedrock key details changed outside AI Term; add the key again`). `guardedFetch` allows plain http only when its caller marks it keyless-local (`plainLocal`, Ollama only) and the endpoint's host is 127.0.0.1 (decided from the parsed URL, so port 80 works).
- **Bedrock / Vertex check:** both work with one API key and no cloud CLI login (package docs: Bedrock "API key authentication … takes precedence over any SigV4 credentials"; Vertex "Express mode provides a simplified authentication method using an API key instead of OAuth"). Vertex express keys reach Google's own (Gemini) models only; Claude on Vertex needs a Google Cloud login and is not offered.
- **Models and tests:** each key carries its model ids (`deployments`, at most 40). `keys.test` sends one tiny request per model (16 output tokens, 15 s, no redirect: Chat Completions, Bedrock Converse, Vertex generateContent) and keeps only the HTTP status or a fixed reason (`src/daemon/providers/direct.ts`). Only a `ready` model is offered (`testedModels`) and started (`Model must pass its test first`). Ollama: `GET /api/tags` (5 s, 256 KiB, valid ids only, at most 40) replaces its model list; each listed model counts as tested (`src/daemon/providers/ollama.ts`). Ollama has no Keychain entry at all; `withSecret` refuses it.
- **Routing:** no CLI can run these keys, so `keyEngine` and `route()` always pick AI Term's agent, even with `keysRunOn: 'cli'`; the CLI branch refuses them too (`Key provider does not match engine`).
- **Cost and budgets:** no catalog prices for these providers; `findPrice` uses a price override (any model id, `/settings` p) or none (`price ?`, the agent pauses once per model and run when any limit is set). Ollama is priced at 0 unless you set an override for that model (Ollama can also serve billed cloud models), so reservations and budgets apply with that amount. Overrides are keyed by model id across providers (a Foundry deployment and an OpenRouter model with the same id share one); accepted, budget math only. The handoff note writer stays on Anthropic, OpenAI and Foundry (the providers that one-shot was reviewed for).
- **Not added:** `.env` import for these providers (a key needs its model ids first).

### 12.4 v0.3 splits

- **Opening:** the homepage marks 2–4 agents with Space and `v` calls `split()` (`src/client/split.ts`) with their ids in list order. `split-layout.ts` fits 2 or 3 panes side by side (3 falls back to two on top and one full width below) or 4 as 2×2, each at least 40×10 including its header; fewer than two fitting returns the first agent for a normal attach.
- **No protocol change:** the daemon lets one connection own one attached agent (§6 ownership), so each pane opens its own connection (`connect()` from the CLI, `autoStart: false`) and sends `sessions.attach {cols: pane width, rows: pane height − 1}`. Separate sockets also keep a flooding pane's bytes from queueing ahead of the focused pane's echo. Leaving sends `sessions.detach` per pane, so sizes follow §5 (preview size, or the normal attach that follows).
- **Rendering:** each pane is a client mirror (`split-pane.ts`) with the bar's passthrough and `BodyRenderer` offset to the pane. Changed cells only, inside synchronized output; every frame ends with the real cursor on the focused pane. The focused pane keeps the bar's 8 ms frame spacing and same-tick echo; other panes draw at most at 30 fps. Flood cap: a pane's mirror parses at most 8 KB per event-loop turn, and past 1 MB queued its socket pauses (the daemon then pauses that PTY) until it is under 256 KB.
- **Input:** `split-input.ts` splits stdin into focused-pane keys, Ctrl+\ (raw `0x1c`, kitty `CSI 92;5u`, modifyOtherKeys `CSI 27;5;92~`; kitty releases swallowed), Ctrl+E (as §6) and SGR mouse reports; nothing inside a bracketed paste is interpreted. The real terminal stays in `?1003` + `?1006` for the whole split; `split-mouse.ts` re-encodes each event in the agent's tracking level and encoding; a press focuses the pane under the pointer first, and only the focused pane receives mouse input (a drag stays with its pane; wheel or motion over another pane is dropped). Output a pane printed while in the background never reaches the terminal live after it takes focus: the pane counts bytes and forwards only slices that arrived after focus, then replays its modes once the backlog is parsed. A pane's theme query (`CSI ? 996 n`) is answered from the probed background, never forwarded, since the reply would come back as input to whichever pane is focused by then (v0.3 gate). Pane key: Ctrl+\, because Claude Code 2.1.299 binds Ctrl+] (`app:openArtifact`) and lists Ctrl+\ as a key it never binds; Codex's help lists no keys (its install under `~/.codex` was not read).
- **S15 in a split:** only the focused pane's passthrough reaches the terminal (modes, cursor shape, title, bell, OSC 52 writes); background panes are cells only. Pane mouse modes stay in their mirrors, and kitty flags are set (`CSI = flags ; 1 u`) rather than pushed, so panes never share stack entries. On focus change the terminal takes the new pane's keyboard modes, cursor shape and title (`Passthrough.restore()`). OSC 52 reads are always dropped; terminal queries follow the bar's table per pane (XTWINOPS 18 answers the pane's size).
- **Exits:** an ended agent's pane stays with its exit state; Ctrl+\ closes ended panes; `session.removed` closes a pane at once; a takeover marks it `attached elsewhere`. One pane left returns for a normal attach.
- **Latency gate:** `scripts/measure-split.ts`, results in `docs/testing/v0.3-split-latency.json` and PROGRESS.md.
