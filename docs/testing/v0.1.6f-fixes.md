## Installed CLI facts (Claude Code 2.1.296, Codex 0.160.1)

Checked with `claude --help`, `codex --help`, `codex login --help` and `codex login status --help`, plus parse checks. Each value was also tried next to a bogus control value, which the CLI rejected, so the `--version` and `--help` probes really validate their arguments.

| Flag | Result |
|---|---|
| Claude `--permission-mode=default` | Accepted. Help lists the choices `acceptEdits, auto, bypassPermissions, manual, dontAsk, plan`. The binary's canonical list is `["acceptEdits","auto","bypassPermissions","default","dontAsk","plan"]`, and it maps the user-facing `manual` to `default` (`e==="manual"?"default":e`). So `default` is the canonical value, and we keep the spelling D40 names. |
| Codex `--ask-for-approval=on-request` | Exists. The possible values are now only `on-request` and `never`. |
| Codex `--sandbox=workspace-write` | Exists, with the values `read-only`, `workspace-write` and `danger-full-access`. |
| Codex `--no-daemon` | Exists as a top-level option: "Run without the shared background server, even if it is already running". **Codex rejects it twice:** "the argument '--no-daemon' cannot be used multiple times". |
| Every argv `buildArgs` now emits | Parses in the installed CLIs: Claude ask/dontAsk, Codex ask/dontAsk, and the full Foundry ask argv with one `--no-daemon`. |

New in Codex 0.160.1: `--approve-for-me` routes approvals through automatic review. It isn't on our forbidden list and isn't used; the exact-argv tests would catch it being added.

**Does `codex login status` need `--no-daemon`?** No.
- `codex --no-daemon login status` gives the same result as `codex login status`.
- `codex login status --no-daemon` is rejected (exit 2): the flag is valid only before the subcommand.
- With `CODEX_HOME` pointed at an empty temp folder, both forms report "Not logged in" (exit 1), even though a logged-in shared daemon (0.162.1) was running. So the status command reads the login from the `CODEX_HOME` in its own env, not from the daemon.
- Removing `AZURE_OPENAI_API_KEY` doesn't change the result.
- `engines.ts` is unchanged.
