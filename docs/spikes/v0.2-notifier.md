# v0.2.1 notifier spike

Snapshot: macOS 26.5.1 (25F80), arm64, Swift 6.3.2, main starting at 9bacfae. Source and harness are in `spikes/notifier/`; no product wiring or dependencies. The architecture has D36/D42/D43 but no §12.1 Notifications subsection or D51 entry. This spike follows the user's brief for those missing details and does not reopen pinned decisions.

**Verdict: no-go for claiming D36/D43 proved on this machine yet.** Build, signing, validation and local callback transport pass. Both runtime launch modes fail authorization with UserNotifications code 1 (NotificationsNotAllowed); no notification was posted. The UI tool could not observe a permission/settings window (`cgWindowNotFound`). Notification display, physical sound and real click paths need Yaniv. This is an authorization block, not proof that the platform cannot support notifications. v0.2.1 is partial.

## Built

- Minimal script-built app, no Xcode project: Info.plist names AI Term, `local.aiterm.notifier`, LSUIElement, ad-hoc signed. No provider names, logos or identifiers. No custom icon supplied; actual notification icon is unobserved.
- Swift 6 strict-concurrency helper: request alert+sound authorization, post title/body/default sound, session UUID in userInfo, threadIdentifier = session UUID. The delegate handles the default click and sends only `{"clicked":"<sessionId>"}` plus newline over the Unix socket supplied in argv.
- All input is argv. UUID, title ≤80 Unicode scalars, body ≤200, control/format exclusions, known flags, bounded lifetime, exact `click.sock` inside a private, same-user, nonsymlink spike temp directory. Socket modes/type/ownership are checked before launch and callback; no shell/network/process spawning in Swift. Unix callback send is small and bounded by a one-second send timeout; errors are fixed text.
- Node harness owns a fresh temp root/socket, compares callbacks against its two session UUIDs, reports fixed/numeric helper diagnostics, and launches either via argument-array spawn or `/usr/bin/open -n -a`. `quit-helper` stops only tracked processes whose executable still matches this bundle. `probe` tests callback transport only. `second` posts then exits for the cold-click test, and `stack` posts same/different-session notifications.
- `verify.mjs`: 26 argument boundary cases and a UUID-only callback probe. Unknown flags, duplicate fields, invalid UUIDs, text bounds, controls, unsafe paths/modes and a symlinked root all refused with fixed errors.

## D43 comparison and recommendation (not built)

| Option | Needs / asks | Risks and limits |
|---|---|---|
| `open -a Terminal <generated .command>` | A private executable text file, a fixed interpreter, an absolute resolved ai executable, strictly validated session UUID, correct shell quoting, Launch Services/Terminal document open. Does not use Terminal's `do script` AppleEvent; expected no Automation prompt. | OS/Terminal file-opening or quarantine warnings may still appear; not tested here. Terminal preferences may choose a tab rather than a new window. File creation/cleanup and the exact new-window guarantee need proof. Never interpolate notification title/body, project paths or unvalidated text into the command. |
| AppleScript `tell application "Terminal" ... do script ...` | Apple Events Automation consent from the invoking signed helper to Terminal; app usage description and any relevant entitlement if sandboxed later. A command string plus both AppleScript and shell quoting, and explicit window/tab behavior. | Automation can be denied; adds a permission and injection surface. Better control of target/window semantics, but exact behavior and consent UI untested. No access was requested in this spike. |

Recommend evaluating the `.command`/Launch Services route first for v0.2.4, because it avoids Automation control of Terminal. Treat the new-window requirement as a separate acceptance gate; if Terminal settings cause tabs, do not claim D43 complete. If exact new windows require AppleScript, request and explain Automation permission only when Yaniv explicitly chooses that tradeoff. This recommendation is an engineering comparison from local system declarations, not a live permission measurement.

## Recommended v0.2.4 design and fallback

- After Allow/display/warm-click proof, use one stable AI Term helper bundle launched through Launch Services, with a retained delegate and fixed identity. Keep it alive while notifications need clicks; ephemeral per-event processes are not a proved cold-click strategy.
- Follow D42: always notify a transition into waiting/failed turn; done only when that agent is not attached. Content should use bounded sanitized labels, never prompts, tool input, replies, errors or secrets. Group by session.
- Route a revalidated UUID-only click through the daemon's private endpoint, select/attach that session if a client exists, and use the future D43 launch path otherwise. Reject stale/nonexistent session IDs. This is a recommendation only; no daemon/protocol/client changes here.
- Cold relaunch needs a separately reviewed durable route or a daemon-owned long-lived helper. macOS may deliver the response without original argv; the spike intentionally refuses to invent state recovery from userInfo, UserDefaults or files. A daemon restart, stale socket and callbacks for old sessions must be covered before product wiring.
- Current **no-go fallback**, as requested: sound plus an AI Term notification without click-through until the v0.5 app, only if notification permission is granted. With permission denied, remain on homepage status and a fixed warning; do not force sound through Focus or claim an OS banner was delivered. The fallback itself still needs display/sound proof.

## Yaniv's manual replay

Each shell line starts in the repo. Build output stays under spikes/notifier/build; runtime files stay in its own random temp directory.

1. `cd ~/ai-term && node spikes/notifier/build.mjs`
2. `cd ~/ai-term && node spikes/notifier/verify.mjs`
3. `cd ~/ai-term && node spikes/notifier/harness.mjs` — type open; Allow the AI Term permission prompt. If code 1, enable AI Term under System Settings → Notifications, then type open again. Record name/icon/sound.
4. `cd ~/ai-term && node spikes/notifier/harness.mjs` — in this harness type open, then click the banner; expect a clicked UUID. Type quit-helper, then direct, and repeat.
5. `cd ~/ai-term && node spikes/notifier/harness.mjs` — type stack, inspect grouping; type second, wait for exit-after-post, type quit-helper, then click the second notification. Record relaunch and callback separately; type quit to clean up.

Use one harness at a time (steps 4/5 describe independent replays). The current helper will reject a no-args cold relaunch; report it rather than manually opening the app to make the click appear to work.
