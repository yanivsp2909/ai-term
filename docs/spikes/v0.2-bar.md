# v0.2 top bar spike (redraw vs raw)

Step v0.2.1b, for D39: a one-row AI Term bar above an attached session. Raw passthrough can't keep a row, because agents use absolute cursor positions, clear the screen and reset scroll regions. So the client would keep its own `@xterm/headless` copy of the agent's screen and redraw it under the bar (the tmux model).

**The question:** is that as fast and as faithful as raw passthrough?

**Answer: go, with the limits listed below.**
- Redraw adds 0.4 to 0.6 ms to typing echo at p95, against a 2 ms gate.
- It uses 2.9% of one core while an agent streams output, against a 25% flag.
- It matches the program's own screen cell for cell in every deterministic test, and Claude Code and Codex both work.
- What it loses is link targets (OSC 8), fancy underline styles, inline images, and a little CPU under heavy floods. One condition: the mirror needs a modern character-width table.

Built and measured by Claude Code (Opus 5.5) from a prompt written for Codex. Throwaway code; nothing in `src/` or `tests/` changed.

## Setup

- **Machine and tools:**
  - macOS (Darwin 25.5.0) arm64, Node 26.3.0, node-pty 1.2.0-beta.15, @xterm/headless 6.0.0.
  - vim 9.1, less, `/usr/bin/top`. htop is **not installed**, so `top` stands in for it.
  - Claude Code 2.1.296, Codex 0.160.1.
- **Harness** (`spikes/bar/bar.ts`): runs one program in a node-pty PTY at **rows − 1** and shows it full screen in one of two modes.
  - `--mode raw`: PTY bytes go straight to stdout, like today's `attach.ts`, with the same `HomeKeyFilter` on input.
  - `--mode redraw`: bytes go into a client-side headless xterm. A cell diff draws rows 2..N, and row 1 is the bar, drawn with the product `Grid`, `diffFrame` and slate theme. Each frame sits inside synchronized output (`ESC[?2026h … l`), and only changed cells are written.
- **Driver** (`spikes/bar/drive.ts`):
  - Runs the harness inside an outer node-pty PTY of **120×40**, so the agent area is 120×39.
  - A headless xterm with modern character widths plays the user's terminal. It shows what the user would see, and it answers DA and cursor queries like a real terminal would.
  - Fidelity reference: the same program run **directly** in a 120×39 terminal, with no harness.
  - Compared cell by cell: character, width, color mode and value (default, 16-color, 256-color, RGB) and 9 attributes. Also the cursor position, the mouse, paste, cursor-key and focus modes, and the window title.
- Same measuring method as the renderer spike: timing inside a PTY, `ps -o %cpu` samples every second, plus `process.cpuUsage()` over the whole run. The output is bytes delivered to the PTY, not pixels painted by Terminal.app.

## Typing latency

Measured from writing one key into the outer PTY until that character is readable on its output (escape sequences stripped). This covers both PTY hops and the harness. 500 keys per run, 15–25 ms apart. Two full rounds were run; both are shown as round 1 / round 2. Times are in ms.

| Program | Mode | p50 | p95 | p99 | max | redraw − raw (p95) |
|---|---|---:|---:|---:|---:|---:|
| echo (`spikes/bar/echo.js`) | raw | 0.52 / 0.52 | 0.81 / 0.75 | 1.06 / 1.05 | 3.94 / 3.77 | |
| echo | redraw | 0.92 / 0.91 | 1.21 / 1.24 | 1.66 / 1.71 | 10.47 / 4.53 | **+0.40 / +0.49** |
| vim (`vim -Nu NONE`, insert mode) | raw | 0.61 / 0.59 | 0.85 / 0.82 | 1.00 / 0.92 | 1.49 / 1.41 | |
| vim | redraw | 1.12 / 1.12 | 1.47 / 1.45 | 1.83 / 1.64 | 2.96 / 1.86 | **+0.62 / +0.63** |

**Gate (redraw p95 within 2 ms of raw): pass**, with about 1.4 ms to spare. Each frame took about 0.4 ms to render at p50 and under 0.6 ms at p95 (inside the harness).

**One fix was needed to get there.** The first redraw run had vim at p95 2.95 ms against 0.92 ms raw: +2.03 ms, a fail. Rendering was only 0.5 ms of that.
- **Cause:** xterm parses a `write()` on a later timer tick, which takes at least 1 ms in Node, unless the write follows user input.
- **Fix:** after forwarding a keystroke, the harness calls the public `term.input('', true)` to flag user input, and draws the frame in the same tick when no frame is pending.
- Under a flood, frames are still limited to one every 8 ms.

## CPU

`process.cpuUsage()` covers the whole run, as % of one core. `ps` gives the 1-second samples. "Ctrl+E exit" is the time from Ctrl+E until the harness is gone, measured while the output is still flooding (it includes a 20 ms exit delay).

| Load | Mode | CPU (cpuUsage) | ps avg / max | bytes/s to terminal | frames | program output | Ctrl+E exit |
|---|---|---:|---:|---:|---:|---:|---:|
| `spikes/renderer/noise.js`, 30 s | raw | 0.74% | 0.10 / 0.8% | 4,061 | n/a | n/a | 26 ms |
| `noise.js`, 30 s | redraw | **2.89%** | 2.27 / 5.7% | 2,988 | 995 (33/s) | n/a | 29 ms |
| `yes` flood, 15 s (extra) | raw | 79.4% | 78.1 / 80% | 84.8 MB/s | n/a | 80.6 MB/s | 26 ms |
| `yes` flood, 15 s (extra) | redraw | **91.9%** ⚠ | 91.6 / 92% | 13.4 KB/s | 2,071 | 70.7 MB/s | 25 ms |

- **Gated load (`noise.js`):** redraw uses 2.9% of one core, far under the 25% flag.
- **The extra `yes` flood:** this is the worst case, an agent dumping a huge file. It **exceeds 25% in both modes**: redraw 92%, raw 79%.
  - Redraw parses everything it receives, but sends the terminal only 13 KB/s instead of 85 MB/s, so the terminal app itself has almost nothing to paint. Terminal.app's own CPU wasn't measured.
  - Ctrl+E stays instant in both modes.
- **In the product:** the daemon's mirror already parses every session. Redraw adds a second parser, in the client, for the one attached session.

## What redraw mode handles explicitly

Raw passthrough gets all of this for free. In redraw mode nothing reaches the real terminal unless `spikes/bar/passthrough.ts` sends it.

| Agent sends | Redraw does | Why |
|---|---|---|
| DECSET/DECRST 1 (cursor keys), 9/1000/1002/1003 (mouse tracking), 1005/1006/1015 (mouse encoding), 1004 (focus), 1007 (alt scroll), 2004 (paste), 12 (blink), 66 and `ESC =`/`ESC >` (keypad), 2031 (theme reports) | forwards it, and the mirror applies it too | these describe the real terminal's input or look, not screen content |
| 1016 (SGR-pixel mouse) | refuses it | pixel rows can't be shifted by one cell row without knowing the cell height. Claude Code only ever turns it off. |
| 25 (cursor visible), cursor position | tracked; the cursor is drawn at mirror position + 1 row at the end of each frame and hidden while painting | the cursor would jump across changed cells in terminals without synchronized output |
| DECSCUSR (cursor shape) | forwarded | |
| OSC 0/1/2 (title), `CSI 22/23 t` (title stack) | forwarded | position-free |
| OSC 7 (cwd), OSC 9 / 777 (notifications), BEL | forwarded | position-free |
| OSC 4/10/11/12 set, OSC 104/110/111/112 reset | forwarded | colors match raw mode; RESET_MODES restores them on exit |
| OSC 10/11 query | answered from a one-time startup probe of the real terminal | the mirror doesn't answer them, and a forwarded query's answer would arrive after the mirror's own DA1 answer |
| OSC 4 / OSC 12 query | dropped | can't be answered faithfully |
| **OSC 52 write (copy)** | **forwarded** (up to 1 MB) | copying is position-free, and raw mode allows it already |
| **OSC 52 read (paste query)** | **dropped** | it would hand your clipboard to the agent |
| **OSC 8 hyperlink** | **dropped**, text kept | the mirror stores links, but the cell's link id isn't public API in @xterm/headless 6.0.0 |
| kitty keyboard (`CSI > u` push, `CSI < u` pop, `CSI = u` set, `CSI ? u` query) | forwarded and answered from a flag stack, only if the startup probe found kitty support; otherwise ignored, like a terminal without it | the mirror doesn't speak it, and the answer must come before the mirror's DA1 |
| modifyOtherKeys `CSI > 4 ; n m` | forwarded | |
| DA1, DA2, DSR/CPR, DECRQM, DECRQSS | the mirror answers | answers are about the agent's own screen and coordinates |
| `CSI 18 t` (text area size) | answered with the agent's size | the real terminal would report one row too many |
| `CSI 14 t`, other window ops | dropped | |
| `CSI ? 996 n` (theme query) | forwarded; the reply comes back as input | |
| the agent's own synchronized output (2026) | honored: no frame while it's on, at most 150 ms | no half-drawn agent frames |
| RIS `ESC c` | resets the forwarded modes on the real terminal | |
| Sixel, kitty graphics, iTerm2 images | dropped (the mirror ignores them) | no agent uses them today |
| **Input: mouse reports** | row − 1. A press or wheel on the bar is dropped, along with that press's release. A drag or release on the bar becomes row 1. | |
| **Input: Ctrl+E** | the existing `HomeKeyFilter` runs first, then mouse rewriting | |

The startup probe sends OSC 10, OSC 11, kitty query and DA1 once, before the agent starts. It waits at most 250 ms; every terminal answers DA1, so it's usually much faster.

## What redraw mode loses compared with raw

1. **Hyperlink targets (OSC 8).** Codex sends them (3 links on its first screen). The text stays, and terminals still detect plain URLs on ⌘-click, but link text that isn't the URL loses its target. A client-side OSC 8 tracker is possible later.
2. **Underline style and color.** Curly or dotted underline and SGR 58 underline color become a plain underline. The mirror stores them, but has no public API to read them.
3. **Character widths become a three-way agreement:** agent, mirror and terminal.
   - The built-in Unicode 6 table is wrong for emoji (the matrix shows a 25-cell failure). A modern table is required in both the client mirror and the daemon mirror.
   - The spike's 41-line approximation is not a product table. The product needs `@xterm/addon-unicode11` or `@xterm/addon-unicode-graphemes`, which is a new dependency for Yaniv to approve, or its own table.
   - Where the terminal still disagrees (Terminal.app, iTerm2 and Ghostty differ on some emoji sequences), absolute positioning after every non-ASCII character keeps the damage inside that cell.
4. **Terminal identity.**
   - DA2 and DECRQM answers describe xterm.js, not your terminal, and XTVERSION gets no answer.
   - OSC 4 and OSC 12 color queries get no answer.
   - OSC 10/11 come from the startup probe, so they go stale if you switch theme mid-session (2031 theme reports still pass through).
5. **Kitty keyboard** works only through the startup probe. The test terminal had no kitty support, so this needs a manual check in Ghostty or iTerm2.
6. **Inline images** (sixel, kitty, iTerm2) are dropped.
7. **CPU under floods:** about 12 points of one core more for a `yes` flood (92% vs 79%), and the program's throughput is 70.7 MB/s instead of 80.6 MB/s. In exchange, the terminal receives 13 KB/s instead of 85 MB/s.
8. **Latency** is 0.4 to 0.6 ms higher at p95. That needs the user-input fast path; without it the cost is 2 ms.
9. **Mouse:** SGR-pixel mode is refused. A terminal selection (Option-drag) can now include the bar row.
10. The agent gets **one row less**, by design.

**What redraw fixes:** raw passthrough at rows − 1 is not an option.
- **`less`** scrolls by printing at the bottom of its screen. In a terminal one row taller, that isn't the terminal's bottom row, so every `less` screen is off by a row (1,130+ cells).
- **Leaving the alternate screen** (vim, less, any full-screen tool run in a shell session) shows the terminal's own normal screen in raw mode, which today means your shell from before `ai`. Redraw shows the program's real normal screen.
- **Size reports** (`CSI 18 t`) are right.
- **Floods** reach the terminal at most 120 times a second.

## Recommendation

**Go, with the limits listed above.**
- Accept losses 1–2 and 4–7 for v0.2. Make the OSC 8 tracker a follow-up.
- The modern width table (loss 3) is a precondition, not a follow-up.
- Keep the window-title fallback only if Yaniv's manual feel test finds flicker or lag that this headless measurement can't see.

**Rough size of the real implementation:** about 600–700 lines of product code plus about 300 lines of tests. Probably two sessions, for example a renderer and passthrough step, then a bar and attach-switch step.

| File | Change |
|---|---|
| `src/client/attach.ts` | output goes to a client mirror instead of stdout; input goes through mouse rewriting; asks the daemon for rows − 1. Lifecycle, signals and cleanup stay. |
| `src/client/session-screen.ts` (new) | client mirror, frame scheduling (≤ 1 frame / 8 ms), the agent-sync wait, the user-input fast path, drain backpressure |

## Found along the way (not fixed: spike only)

- **D39 and §12.1 don't exist in `docs/architecture.md`.** The decisions log jumps from D35 to D40, and the frame bar is only §12's v0.2 bullet. The prompt's description of D39 was used.
- **`RESET_MODES` (`src/client/terminal-modes.ts`) doesn't turn off mode 2031**, which Claude Code turns on. After Ctrl+E out of Claude Code, a terminal that supports 2031 (Ghostty, kitty, recent iTerm2) keeps sending theme-change reports into the homepage. Not checked in a real terminal.
- **htop isn't installed**, so `top` stood in for it.
- **Codex's update notice** doesn't close on Esc within about 1.3 s, and Enter on it means "Update now". In the product, a user attaching to a fresh Codex session lands on that menu. Ctrl+C skips it.
- An idle `codex --no-daemon` TUI from earlier is still open in `~/ai-term` (0% CPU, no repo changes). It wasn't touched.

## Feel test for Yaniv (about 2 minutes)

Use your normal terminal, at least 100×30. In each one:
- type for a few seconds;
- in vim, click somewhere, scroll with the trackpad, and click the bar row (nothing should happen);
- resize the window once.

Judge whether typing feels identical, whether anything flickers or tears, whether the colors match, and whether the cursor shape and blink match. Ctrl+E leaves any of them.

```sh
cd ~/ai-term
cp spikes/bar/render.ts /tmp/bar-feel.ts
# 1. vim, raw passthrough (today's behavior; no bar, bottom row unused). :q! to quit
node --import tsx spikes/bar/bar.ts --mode raw -- vim -Nu NONE -i NONE -n -c 'set mouse=a' -c 'syntax on' /tmp/bar-feel.ts
# 2. vim, redraw with the bar
node --import tsx spikes/bar/bar.ts --mode redraw -- vim -Nu NONE -i NONE -n -c 'set mouse=a' -c 'syntax on' /tmp/bar-feel.ts
# 3. Claude Code, raw, then 4. redraw. Type in the box but DON'T press Enter (that sends a real request). Ctrl+C twice quits.
node --import tsx spikes/bar/bar.ts --mode raw --agent claude
node --import tsx spikes/bar/bar.ts --mode redraw --agent claude
```

Optional:
- `node --import tsx spikes/bar/bar.ts --mode redraw --agent codex`. On the update menu press Ctrl+C, **not Enter**, which means "Update now".
- `node --import tsx spikes/bar/bar.ts --mode redraw --unicode 6 -- node spikes/bar/patterns.js` shows the emoji-width problem; Ctrl+C quits.
- In Ghostty or iTerm2, repeat step 4 to check the kitty keyboard path, for example Shift+Enter in Claude Code's box.
- If you install htop: `node --import tsx spikes/bar/bar.ts --mode redraw -- htop`, then check colors, a click, and F10 to quit.

## Security notes

- **Processes:**
  - Every process is spawned with argument arrays: node-pty `spawn` and `execFile('/bin/ps', […])`. No `exec`, `execSync` or `shell: true`.
  - Every process I started was stopped; no `ai-bar-spike-*` temp folders remain.
  - Yaniv's daemon and `~/.ai-term` were never used.
- **Environment:**
  - Test programs get a literal env: PATH, HOME, LANG, TERM, COLORTERM, TERM_PROGRAM and LESSHISTFILE=-.
  - Agents get exactly the daemon's recipe (`buildSpawnEnv` account, `buildArgs` Ask). The driver also drops this Claude Code session's own `CLAUDECODE` and `CLAUDE_CODE_*` markers, as if the daemon had been started from a plain shell.
  - The harness never logs an env.
- **Private files:** nothing under `~/.claude`, `~/.codex`, `~/.ssh`, the keychain or any `.env` was read.
- **Agents:** no prompt was sent to either agent. The agent driver writes only letters, Ctrl+C and Ctrl+E, never `\r`.
- **Clipboard:** an OSC 52 clipboard read is dropped, so the agent can't read your clipboard through the bar.
