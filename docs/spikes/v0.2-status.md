**Version:** `claude --version` prints `2.1.296 (Claude Code)`. Path: `~/.local/bin/claude` → `~/.local/share/claude/versions/2.1.296`. **Verified.**

**Hooks per session: Verified.**
- Run 1: `node spikes/status/run-claude.mjs hooks` runs `claude -p "reply with ok" --settings /tmp/aiterm-spike/claude-settings-hooks.json --output-format stream-json --verbose --include-hook-events` in `/tmp/aiterm-spike/proj`. Exit 0, 5.4 s.
- Our command hooks logged `SessionStart`, `UserPromptSubmit`, `Stop` and `SessionEnd` (reason `other`). No tool ran, so there were no tool events.
- `--settings` also accepts an inline JSON string (`--help`: "Path to a settings JSON file or a JSON string"). The file must be a regular file of at most 2 MiB (Docs: cli-reference).

**Merge, not replace: Verified.**
- In the same run, a project hook at `/tmp/aiterm-spike/proj/.claude/settings.json` also fired, on SessionStart and Stop.
- The user's own SessionStart hooks also ran: three handlers appeared in `--include-hook-events`. Their content was not recorded.
- Docs (hooks): "Hook entries merge across settings levels rather than replacing each other", and "If you define the same handler in more than one settings file, it runs once."
- `--settings` sits second in precedence, below managed settings only (Docs: settings).

**Things that can switch our hooks off:**

| Thing | Effect | Evidence |
|---|---|---|
| Workspace trust | In an **interactive** session, hooks from every settings file are held back until the user accepts the trust dialog. The status line likewise: "Status line command skipped: workspace trust not accepted". `-p` counts as trusted. | Docs plus binary string |
| `--bare` / `CLAUDE_CODE_SIMPLE` | Turns off `--settings` hooks too. The docs say only "auto-discovery". | Binary: "settings-file, flag, policy, and plugin hooks never fire there" |
| `--safe-mode` | All hooks off | `--help` |
| `disableAllHooks`, managed `allowManagedHooksOnly` | Blocks user, project, local and flag hooks | Docs |
| Managed `allowedHttpHookUrls` | Can block the URL | Docs plus binary |
| `--setting-sources ""` | Can't remove flag or policy settings (`t.add("flagSettings"),t.add("policySettings")`), but drops the user's other settings too | Binary |

## 3. Hook types, payload, blocking, timeouts

**Types: Verified (binary schema).** `command`, `http`, `mcp_tool`, `prompt`, `agent`.
- **HTTP hook fields:** `url`, `headers`, `allowedEnvVars`, `timeout` (seconds), `onFailure`, `if`, `statusMessage`, `once`. There is no `async` field: async is command-only (Docs).
- **SessionStart and Setup accept only `command` (and `mcp_tool`).** Verified: our `http` hook on SessionStart never fired. Docs (hooks): "Only `type: "command"` and `type: "mcp_tool"` hooks are supported."

**HTTP request: Verified with `spikes/status/receiver.mjs`.**
- `POST` to the configured path.
- `Host: 127.0.0.1:<port>`, no `Origin`, `Content-Type: application/json`.
- The body is Claude's native hook JSON.
- The header `x-ai-term-session: $AITERM_SPIKE_TOKEN`, with `allowedEnvVars: ["AITERM_SPIKE_TOKEN"]`, arrived interpolated from the process env.
- Binary: loopback is explicitly allowed ("Loopback (127.0.0.1, ::1) is allowed for local dev"). Known credential env names are never interpolated, and CR, LF and NUL are stripped from header values.
- With Claude's sandbox on, the POST goes "via sandbox proxy". Whether that reaches 127.0.0.1 is **Unknown**.

**Common payload: Verified (keys seen) plus Docs.**
- `session_id` (Claude's id, not ours), `transcript_path`, `cwd`, `hook_event_name`, `prompt_id`, `permission_mode`, `effort`.
- Per event:
  - `UserPromptSubmit.prompt`
  - `Stop.{stop_hook_active, last_assistant_message, background_tasks, session_crons}`
  - `SessionStart.source`
  - `SessionEnd.reason`
  - `Notification.{message, title, notification_type}`
  - `PermissionRequest.{tool_name, tool_input, permission_suggestions}`
  - `StopFailure.{error, error_details}`
- **Sizes:** `tool_input` carries the full command or file content (a Write of a big file), and `last_assistant_message` the whole reply. Bodies can easily exceed 64 KB.

**Blocking and timeouts:**

| Behaviour | Evidence |
|---|---|
| Hooks run in parallel and block until done ("By default, hooks block Claude's execution until they complete") | Docs |
| Defaults: 600 s for command, http and mcp_tool; 30 s for prompt; 60 s for agent; 30 s on UserPromptSubmit; 10 s on MessageDisplay | Docs. Binary `lu=600000` for http. |
| A slow hook (server answers after 4 s, `timeout: 1`) shows as `hook_response … outcome cancelled`. A hook to a closed port shows as `outcome error … ECONNREFUSED`. The turn still succeeded: total 6.0 s against 5.4 s without them. | **Verified, run 2** (`node spikes/status/run-claude.mjs slow`) |
| A failed or timed-out hook is non-blocking unless `onFailure: "block"` (2.1.295+) | Docs plus binary |
| **2xx with an empty body = success. 2xx with a JSON object body is parsed as hook output.** `decision: "approve" / "block"` and `continue: false` are honoured, so a status endpoint that ever returns JSON could approve a permission or stop a session. | Docs plus binary `case"approve":…` |
| Whether a slow `PermissionRequest` hook delays the dialog from appearing (it runs "before" the dialog) | Unknown. Keep its timeout at 1–2 s. |

## 4. Claude context %

- **Hooks: no.** No hook payload carries live context usage. `context_tokens` exists only on SessionStart (resume/fork) and PreModelSwitch. **Docs.**
- **statusLine: yes.**
  - Its stdin JSON has `context_window: {total_input_tokens, total_output_tokens, context_window_size, current_usage, used_percentage, remaining_percentage}` (binary `Q1e`).
  - Docs (statusline): "`used_percentage` … is calculated from input tokens only".
  - It runs at session start, on each assistant message and on `refreshInterval`, debounced to 300 ms (Docs).
- **Settable via `--settings`: yes.** It is a normal settings key (binary schema), so `--settings` can set it. But flag settings outrank user settings, so **AI Term's statusLine would replace the user's own status line** in that session.
- It is gated by workspace trust, `disableAllHooks` and `allowManagedHooksOnly`.
- **Doesn't run in `-p`: Verified.** Our statusLine logger never ran in run 1.
- In the TUI it should work: **Test A**.

## 6. Codex terminal signals

Source: `tui/src/notifications/*`, `config/src/types.rs#L683-723`.

**What is emitted:**
- OSC 9: `ESC ] 9 ; <message> BEL`, wrapped in DCS passthrough inside tmux.
- Or a bare `BEL`.
- **Never OSC 777.**

**Triggers (filters):**

| Filter | When | Message |
|---|---|---|
| `agent-turn-complete` | a turn ends | preview of the reply |
| `approval-requested` | command or edit approval, MCP elicitation | "Approval requested: …", "Codex wants to edit …" |
| `plan-mode-prompt` | plan-mode prompt | — |
| `async-question` | the agent asks a question | — |

**Config and defaults:**

| Key | Values | Default |
|---|---|---|
| `tui.notifications` | `true` or a list of filters | — |
| `tui.notification_method` | `auto` / `osc9` / `bel` | `auto` |
| `tui.notification_condition` | `unfocused` / `always` | `unfocused` |

- `auto` picks OSC 9 only for Ghostty, iTerm2, Kitty, Warp and WezTerm (detected via `TERM_PROGRAM`). We set `TERM_PROGRAM=AITerm`, so `auto` means BEL in our PTY.
- With `unfocused`, nothing is emitted until the host reports focus-out (`ESC [ O`), because the TUI enables focus reporting.
- **All three keys can be set with `-c`:** verified that they parse. `"osc777"` is rejected with "expected one of `auto`, `osc9`, `bel`".
- **Title:** while an approval or question is open, OSC 0 becomes `[ ! ] Action Required | …` (`status_surfaces.rs#L387-395`). `-c tui.terminal_title=["activity","run-state","context-remaining"]` parses (verified) and adds `Ready/Working/Thinking/Waiting` and `Context N% left`.
- **BEL pitfall:** Codex also ends OSC 0, 8 and 52 with BEL. Only a BEL outside an escape sequence is a bell. xterm.js's parser already separates `onBell` from OSC terminators.
- Real emission inside a PTY has not been run: **Test C**.

## 8. Per session through argv or env only

**Claude: yes. Verified.**
- `--settings <file in ~/.ai-term/sessions/<id>/>`, or an inline JSON string, carries the hooks and statusLine.
- The per-session credential stays out of argv and files. Put it in the session env, for example `AITERM_STATUS_TOKEN`, and reference it as `"$AITERM_STATUS_TOKEN"` in an http hook header with `allowedEnvVars`.
- A variable whose name contains TOKEN interpolated fine (`AITERM_SPIKE_TOKEN`). Only Claude's built-in credential names are refused.
- Caveats:
  - Flag hooks merge with the user's hooks; we can't and shouldn't disable theirs.
  - The trust dialog gates interactive hooks.
  - `--bare` and `--safe-mode` disable them.
  - A flag statusLine replaces the user's statusLine.

**Codex: yes, argv only. Verified parse plus the notify run.**
- Use `-c notify=[…]`, `-c tui.notification_*`, `-c tui.terminal_title=…` and `-c otel.exporter=…`. There is no env route (`CODEX_HOME` would move auth; never).
- Caveats:
  - Any `-c` forces "embedded mode". The TUI warns "Running without the shared background server…" unless `--no-daemon` is also passed (`tui/src/daemon_startup.rs#L54-88`). This also affects v0.1.6's planned Foundry `-c` overrides.
  - Codex hooks are skipped unless trusted (verified), so they are not usable without a trust bypass, which we never pass.
  - Notify inherits the Codex process env in embedded mode, so a per-session token in the env reaches the notify helper.

## 9. Proposed event shape (contract-first, proposal only)

**Consumers:**
- The daemon's status reducer, which sets `SessionInfo.status`, `statusDetail` and `ctxPercent`.
- Through `session.updated`, the homepage cards, the top-bar counts and v0.2 notifications.

**Providers:** four ingress adapters inside the daemon, one per source.

**The artifact:** `spikes/status/status-event.schema.json` for now. In v0.2 it moves into `src/shared/protocol.ts` and `validate.ts`, which are the authoritative artifact because every participant shares the build.

The CLIs are not participants. They send their **native** payloads, which we can't reshape (a Claude http hook POSTs Claude's JSON). So the contract is the normalised event, and each adapter is tested against recorded native payloads like the ones in this doc.

```ts
type StatusEvent = {
  v: 1;
  sessionId: string;          // AI Term UUID, resolved from the per-session credential header, never from the body
  source: 'claude-hook' | 'claude-statusline' | 'codex-notify' | 'codex-otel' | 'terminal';
  event: 'turn-started' | 'tool-started' | 'tool-finished' | 'permission-requested' | 'input-requested'
       | 'turn-completed' | 'turn-failed' | 'session-ending' | 'context-updated';
  ts: string;                 // daemon receive time
  seq: number;                // per-session monotonic, daemon-assigned; older seq is ignored
  detail?: string | null;     // ≤ 80 chars, sanitized: tool name, notification_type, StopFailure error enum. Never prompt/tool_input/reply text
  ctxPercent?: number | null; // used %, only on context-updated
  native?: string;            // e.g. 'Notification:permission_prompt', for debugging only
};
```

**Ingress rules** (these extend S12):
- **Claude:** `POST /v1/status/claude`, `x-ai-term-session` credential.
- **Codex notify:** a tiny `ai` helper that POSTs the argv JSON to `/v1/status/codex`.
- **Terminal signals and OTel:** produced inside the daemon (mirror parser, existing OTLP receiver). They need no new endpoint.
- **Always `204` with an empty body**, because any JSON body is a hook decision in Claude.
- Read only the fields we map, and drop the rest unread: `hook_event_name`, `notification_type`, `tool_name`, `error`, `reason`, `type`, `client`.

| Source → native event | StatusEvent `event` | Status |
|---|---|---|
| Claude `UserPromptSubmit` | turn-started | **running** |
| Claude `PreToolUse` / `PostToolUse` / `PostToolUseFailure` | tool-started / tool-finished | **running** (also ends a pending permission wait) |
| Claude `PermissionRequest` | permission-requested (detail: tool_name) | **waiting** |
| Claude `Notification` `permission_prompt` | permission-requested (late backup) | **waiting** |
| Claude `Notification` `elicitation_dialog`, `elicitation_url_dialog`, `agent_needs_input` | input-requested | **waiting** |
| Claude `Stop` | turn-completed | **done** |
| Claude `StopFailure` | turn-failed (detail: `error`) | **failed** (see plan change 6) |
| Claude `Notification` `idle_prompt` | (ignored) | stays done |
| Claude `SessionEnd` | session-ending (detail: reason) | no change; process exit decides |
| Claude statusLine stdin | context-updated (`used_percentage`) | ctx only |
| Codex notify `agent-turn-complete` | turn-completed | **done** |
| Codex OSC 9 "Approval requested…" / title `[ ! ] Action Required` / bare BEL while working | permission-requested | **waiting** |
| Codex OSC 9 turn-complete preview | turn-completed (backup to notify) | **done** |
| Codex: PTY input after done/waiting (user typed and pressed ⏎) | turn-started (heuristic) | **running** |
| Codex OTel `response.completed` + `conversation_starts.context_window` | context-updated | ctx only |
| Any session: process exit | (existing §5 rule) | exited / error, always wins |

## What changes the v0.2 plan

1. **S12's 64 KB body limit would drop real Claude events.** `PermissionRequest.tool_input` (a Write of a big file) and `Stop.last_assistant_message` can exceed it. A 413 is a non-blocking hook error, so the status signal is lost silently. Options:
   - raise the Claude ingress cap (for example 4 MiB), read only the mapped fields and discard the rest unread; or
   - keep 64 KB and accept missing waiting and done events on big turns.
2. **The status endpoint must answer 204 with an empty body, by protocol, not convention.** A 2xx JSON body is a hook decision in Claude (`approve`/`block`/`continue:false`). S12 already says so; this spike shows why. Give `PermissionRequest` hooks a short `timeout` (1–2 s), so a slow or dead daemon delays the dialog by at most that.
3. **Waiting = `PermissionRequest`, not `Notification`.** The §12 outline's `Notification` matcher (`permission_prompt|elicitation_dialog|agent_needs_input`) is about 6 s late for permissions and only fires when the user "appears to be away". Use it as a backup only. `idle_prompt` adds nothing beyond `Stop`.
4. **Two gaps need a fallback:**
   - Claude's Esc interrupt fires nothing, so the status would stay "running" (Test B).
   - Interactive hooks are withheld until the workspace trust dialog is accepted, so a new folder shows nothing, even though the trust dialog itself is a "waiting" state.
   - Mirror-side heuristics could cover both: no output plus a known prompt, or user ⏎.
5. **Codex: no hooks endpoint.** Codex hooks need trust, and we never bypass it. Use `-c notify` (done) plus the daemon's own mirror parsing of OSC 9, bare BEL and the `[ ! ] Action Required` title (waiting). Force `tui.notification_method="osc9"` and `tui.notification_condition="always"`, because `auto` gives BEL in our PTY and `unfocused` gives nothing until focus-out.
   - Pass `--no-daemon` whenever we pass `-c`, to avoid the embedded-mode warning. This matters for v0.1.6 too (Foundry `-c` overrides).
6. **StopFailure → failed vs the §12 outline's "done, with detail".** The prompt's vocabulary has failed. Decide whether a failed *turn* (process alive) shows ✗ failed, or done plus the detail, so that ✗ stays reserved for process errors.
7. **Claude context % only via statusLine, which replaces the user's own status line** in AI Term sessions, because flag settings outrank user settings and we must not read theirs. Options:
   - accept it;
   - make AI Term's status line print something useful (for example model and ctx); or
   - skip Claude ctx % until Claude exposes it elsewhere.

   **Codex ctx % comes from the OTel logs that §9's usage receiver already plans to collect.** That extends §9 to subscription Codex sessions too, for ctx only, not for cost.
8. Correlation ids differ: Claude `session_id`, Codex `thread-id`/`conversation.id`, AI Term `sessionId`. Map only through the per-session credential.
